# C07. Slowly Changing Dimensions

<div className="chapter-kicker">Chapter C07 · Complete course</div>

Slowly Changing Dimensions (SCD) are techniques used by a Data Warehouse to manage changes over time in dimension attributes.

The central idea is simple:

> **What do we do when a descriptive attribute changes, but we may need to preserve the previous value for historical reporting?**

Examples:

- a customer changes its city;
- a customer moves from the RETAIL segment to PREMIUM;
- an employee changes the department;
- a product changes its category;
- a branch moves to another region.

For an Oracle Data Developer, the most important types are **SCD Type 1 and SCD Type 2**. Type 2 is one of the most common practical DWH concepts.

---

## 1. Why do we need SCD?

Suppose we have:

```
CUSTOMER_ID = 1001
NAME = Ionescu
CITY = Bucharest
```

The customer moves to Brașov.

In the source system, we often simply have:

```
CUSTOMER_ID = 1001
NAME = Ionescu
CITY = Brasov
```

But in a Data Warehouse, the question arises:

```
Where does the customer live now?
```

or:

```
Where did the customer live
at the time of the 2025 transaction?
```

The two questions require different models.

This is where SCD comes in.

---

## 2. The two essential types

### SCD Type 1

The old value is **overwritten**.

History is not preserved.

```
before

CUSTOMER_ID CITY
-----------   ----------
1001 Bucharest
```

After modification:

```
CUSTOMER_ID CITY
-----------   ----------
1001 Brașov
```

We can no longer determine from the DWH that the customer previously lived in Bucharest.

---

### SCD Type 2

We do not simply update the existing row.

Instead:

1. close the old version;
2. insert a new version.

Result:

```
CUSTOMER_SK CUSTOMER_ID CITY VALID_FROM VALID_TO CURRENT_FLAG
----------- ----------- ---------- ---------- ---------- ------------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
245 1001 Brașov 2026-06-01 9999-12-31 Y
```

We now have a full history.

---

## 3. Natural key vs. surrogate key

This concept is fundamental to SCD Type 2.

Suppose the operational system identifies the customer with:

```
CUSTOMER_ID = 1001
```

This is:

```
Business Key
or
Natural Key
```

In the DWH, we introduce a surrogate key:

```
CUSTOMER_SK
```

for example:

```
101
245
387
```

The structure becomes:

```
CUSTOMER_SK surrogate key
CUSTOMER_ID business key
```

Why?

Because the same customer may have several historical versions.

```
CUSTOMER_SK CITY
----------- ----------- ----------
101 1001 Bucharest
245 1001 Brașov
```

Business key is the same:

```
CUSTOMER_ID = 1001
```

but each historical version has a different:

```
CUSTOMER_SK
```

## 4. Typical structure of an SCD Type 2 dimension

A very common design is:

```
CREATE TABLE dim_customer
(
customer_sk NUMBER GENERATED BY DEFAULT AS IDENTITY,
customer_id NUMBER NOT NULL,

customer_name VARCHAR2(100),
city VARCHAR2(100),
segment VARCHAR2(30),

valid_from DATE NOT NULL,
valid_to DATE NOT NULL,
current_flag CHAR(1) NOT NULL,

CONSTRAINT pk_dim_customer
PRIMARY KEY (customer_sk)
);
```

Conceptual:

```
customer_sk
customer_id
descriptive attributes
valid_from
valid_to
current_flag
```

In more complex projects, we may also store:

```
batch_id
source_system
insert_timestamp
update_timestamp
hash_value
```

## 5. Example: SCD Type 1

Initial:

```
CUSTOMER_ID CITY
----------- ----------
1001 Bucharest
```

The staging area receives:

```
CUSTOMER_ID CITY
----------- ----------
1001 Brașov
```

We can update using:

```
UPDATE dim_customer
SET city = 'Brașov'
WHERE customer_id = 1001;
```

Or, in ETL processing, we can use:

```sql
MERGE INTO dim_customer d
USING staging_customer s
ON (d.customer_id = s.customer_id)

WHEN MATCHED THEN
UPDATE SET
d.customer_name = s.customer_name,
d.city = s.city,
d.segment = s.segment

WHEN NOT MATCHED THEN
INSERT
(
customer_id,
customer_name,
city,
segment
)
VALUES
(
s.customer_id,
s.customer_name,
s.city,
s.segment
);
```

This is a typical implementation of:

```
SCD Type 1
```

## 6. When do we use SCD Type 1?

Use it when history is not important.

Examples:

```
correction of a typo
```

for example:

```
Bucharest
```

becomes:

```
Bucharest
```

There is no value in keeping:

```
Version 1: Bucharest
Version 2: Bucharest
```

Another example:

```
customer_name:
IONSCU
```

corrected to:

```
IONESCU
```

Type 1 is appropriate.

## 7. SCD Type 2

Suppose we have:

```
Customer 1001
City = Bucharest
```

Current row:

```
CUSTOMER_SK = 101
CUSTOMER_ID = 1001
CITY = Bucharest
VALID_FROM = 2025-01-01
VALID_TO = 9999-12-31
CURRENT_FLAG = Y
```

At:

```
2026-06-01
```

The customer moves to Brașov.

We don't:

```
UPDATE dim_customer
SET city = 'Brașov';
```

Because that would lose the historical version.

---

## 8. Step 1: Close the old version

```
UPDATE dim_customer
SET valid_to = DATE '2026-06-01',
current_flag = 'N'
WHERE customer_id = 1001
AND current_flag = 'Y';
```

Now:

```
CUSTOMER_SK CUSTOMER_ID CITY VALID_FROM VALID_TO CURRENT
----------- ----------- ---------- ---------- ---------- -------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
```

---

## 9. Step 2: Insert the new version

```sql
INSERT dim_customer
(
customer_id,
customer_name,
city,
segment,
valid_from,
valid_to,
current_flag
)
VALUES
(
1001,
'Ionescu',
'Brașov',
'RETAIL',
DATE '2026-06-01',
DATE '9999-12-31',
'Y'
);
```

Result:

```
SK ID CITY VALID_FROM VALID_TO CURRENT
---  ----  ----------  -----------  -----------  -------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
245 1001 Brașov 2026-06-01 9999-12-31 Y
```

## 10. Time intervals

A good pattern is to treat intervals like:

```
[VALID_FROM, VALID_TO)
```

I mean:

```
VALID_FROM <= event_date
AND
event_date < VALID_TO
```

Avoid:

```
BETWEEN valid_from AND valid_to
```

when `VALID_TO` is the exact beginning of the next version.

For example:

```
Bucharest:
Bucharest: [2025-01-01, 2026-06-01)
Brașov:    [2026-06-01, 9999-12-31)
```

Advantage:

```
We have no overlaps.
We have no ambiguity at the border.
```

## 11. How does a fact table link to an SCD Type 2 dimension?

Suppose:

```
FACT_TRANSACTION
```

with:

```
TRANSACTION_ID
CUSTOMER_SK
TRANSACTION_DATE
AMOUNT
```

We do not use this as the primary dimensional link in the fact table:

```
CUSTOMER_ID
```

as the main link to the dimension.

We put:

```
CUSTOMER_SK
```

Why?

Because the fact row must point to the exact dimension version that was valid at the event date.

---

## 12. Example

Customer:

```
CUSTOMER_ID = 1001
```

has:

```
SK CITY
----  ----------
101 Bucharest
245 Brașov
```

Transaction from:

```
2026-04-10
```

will have:

```
CUSTOMER_SK = 101
```

Transaction from:

```
2026-08-20
```

will have:

```
CUSTOMER_SK = 245
```

So the historical report remains correct.

## 13. Temporal dimension lookup during fact loading

When loading a fact row, we can resolve the correct surrogate key with:

```sql
SELECT customer_sk
FROM dim_customer
WHERE customer_id = :customer_id
  AND :transaction_date >= valid_from
  AND :transaction_date <  valid_to;
```

This is a fundamental DWH pattern.

Conceptual:

```
FACT event data
      ↓
business key
      ↓
DIMENSION
      ↓
the valid version at that time
      ↓
surrogate key
      ↓
FACT
```

## 14. Change detection

In SCD Type 2, we need to detect whether tracked attributes have changed.

Simple version:

```sql
WHERE (d.city <> s.city
         OR (d.city IS NULL AND s.city IS NOT NULL)
         OR (d.city IS NOT NULL AND s.city IS NULL))
   OR (d.segment <> s.segment
         OR (d.segment IS NULL AND s.segment IS NOT NULL)
         OR (d.segment IS NOT NULL AND s.segment IS NULL))
```

But if the dimension has:

```
40
50
100
```

tracked columns, direct comparison becomes cumbersome.

A hash can simplify change detection.

---

## 15. Change Detection with STANYESRD_HASH

For example:

```
STANYESRD_HASH (
NVL(customer_name, '#')
* '|' *
(city, '#')
* '|' *
(segment, '#')
'SHA256'
)
```

We can store:

```
HASH_VALUE
```

in the dimension.

During ETL, we calculate the same hash for the staging row.

If:

```
source_hash = dimension_hash
```

then:

```
NO CHANGE
```

If:

```
source_hash <> dimension_hash
```

then:

```
CHANGE DETECTED
```

and trigger SCD Type 2 processing.

## 17. SCD Type 0

Type 0 means:

```
value never changes
```

Once the attribute has been entered:

```
is kept permanently
```

Example:

```
CUSTOMER_ORIGINAL_REGISTRATION_DATE
```

or:

```
ORIGINAL_SOURCE_SYSTEM
```

ETL does not modify these values.

---

## 18. SCD Type 1

Recap:

```
OLD VALUE
    ↓
overwrite
    ↓
NEW VALUE
```

History:

```
NO
```

Advantages:

```
simple
fast
reduced space
```

Disadvantage:

```
history is lost
```

---

## 19. SCD Type 2

Model:

```
OLD ROW
   ↓
expire old row
   ↓
NEW ROW
```

History:

```
YES
```

Advantages:

```
complete history
correct temporal reporting
auditability
```

Cost:

```
multiple rows per business key
more complex ETL
```

---

## 20. SCD Type 3

Type 3 keeps the history in a limited number of columns.

Example:

```
CUSTOMER_ID
CURRENT_CITY
PREVIOUS_CITY
```

Initial:

```
1001; Bucureşti; NULL;
```

The customer moves:

```
1001 - Brașov - Bucharest
```

If the customer later moves to Cluj:

```
1001 - Cluj - Brașov
```

The older Bucharest value is lost.

So we only have limited history.

---

## 21. SCD Type 4

Type 4 uses two tables.

A table for the current value:

```
DIM_CUSTOMER
```

and a separate table for history:

```
DIM_CUSTOMER_HISTORY
```

For example:

```
DIM_CUSTOMER

1001 - Brașov
```

and:

```
DIM_CUSTOMER_HISTORY

1001; Bucureşti; 2025-01-01; 2026-06-01
```

---

## 22. SCD Type 5 and Type 6

They occur less rarely in ordinary projects and much less in technical discussions than Type 1 and Type 2.

Type 6 is commonly described as a combination of:

```
Type 1
+
Type 2
+
Type 3
```

For example, we can have simultaneously:

```
CUSTOMER_SK
CUSTOMER_ID
CITY
CURRENT_CITY
PREVIOUS_CITY
VALID_FROM
VALID_TO
CURRENT_FLAG
```

The goal is to provide both:

```
complete history
```

and convenient access to:

```
current / previous value
```

---

## 23. Summary of SCD types

| Type | Behavior | History |
|---|---|---|
| Type 0 | Keep the original value unchanged | Original value only |
| Type 1 | Overwrite the existing value | No history |
| Type 2 | Insert a new row for each version | Complete history |
| Type 3 | Store current and previous values in columns | Limited history |
| Type 4 | Keep current data and history in separate tables | Full history in history table |
| Type 5 | Hybrid technique | Depends on implementation |
| Type 6 | Hybrid of Types 1, 2, and 3 | Complete + convenient current/previous access |

For practical Oracle DWH work, **Type 1 and Type 2 are the most important**.

## 24. SCD and incremental load

SCD usually appears in an incremental process.

We do not reload the entire dimension for every run.

A typical flow is:

```
Source
   ↓
CDC / delta / incremental extract
   ↓
Staging
   ↓
Data Quality
   ↓
Lookup DIM
   ↓
Change Detection
   ↓
SCD Type 1
```

For each business key:

```
new record
changed record
unchanged record
```

## 25. SCD and MERGE in Oracle

MERGE is very useful for:

```
SCD Type 1
```

but Type 2 requires special care.

For a changed row, SCD Type 2 requires:

```
UPDATE old row
+
INSERT new row
```

A common implementation therefore uses:

```
UPDATE old versions
INSERT new versions
```

in two set-based operations or through an intermediate staging.

Do not assume that a single simple `MERGE` always implements the entire SCD Type 2 flow cleanly.

---

## 26. Set-based Oracle pattern for SCD Type 2

Suppose:

```
STG_CUSTOMER
DIM_CUSTOMER
```

Identify changed rows:

```sql
SELECT s.customer_id,
       s.customer_name,
       s.city,
       s.segment
FROM staging_customer s
JOIN dim_customer d
  ON d.customer_id = s.customer_id
 AND d.current_flag = 'Y'
WHERE (s.customer_name <> d.customer_name
         OR (s.customer_name IS NULL AND d.customer_name IS NOT NULL)
         OR (s.customer_name IS NOT NULL AND d.customer_name IS NULL))
   OR (s.city <> d.city
         OR (s.city IS NULL AND d.city IS NOT NULL)
         OR (s.city IS NOT NULL AND d.city IS NULL))
   OR (s.segment <> d.segment
         OR (s.segment IS NULL AND d.segment IS NOT NULL)
         OR (s.segment IS NOT NULL AND d.segment IS NULL));
```

---

## 27. Close modified versions

```
UPDATE dim_customer d
SET
d.valid_to = :effective_ts,
d.current_flag = 'N'
WHERE d.current_flag = 'Y'
AND EXISTS
(
SELECT 1
FROM staging_customer s
WHERE s.customer_id = d.customer_id
AND ((s.customer_name <> d.customer_name
        OR (s.customer_name IS NULL AND d.customer_name IS NOT NULL)
        OR (s.customer_name IS NOT NULL AND d.customer_name IS NULL))
  OR (s.city <> d.city
        OR (s.city IS NULL AND d.city IS NOT NULL)
        OR (s.city IS NOT NULL AND d.city IS NULL))
  OR (s.segment <> d.segment
        OR (s.segment IS NULL AND d.segment IS NOT NULL)
        OR (s.segment IS NOT NULL AND d.segment IS NULL)))
);
```

---

## 28. Insert new versions

After detection of the changes, we insert the new versions.

In practice it is safer to have a list of changes in a staging / delta table before, because after UPDATE size no longer contains the same values with which we compared.

Conceptual:

```
STAGING
     ↓
CHANGE_SET
     ↓
UPDATE old DIM rows
     ↓
INSERT new DIM rows
```

This is a more robust pattern.

---

## 29. The most important SCD Type 2 rule

For a business key there must normally be:

```
at most one row with CURRENT_FLAG = 'Y'
```

For:

```
CUSTOMER_ID = 1001
```

this is wrong:

```
SK CURRENT
101 1001 Y
245 1001 Y
```

Correct:

```
101 1001 N
245 1001 Y
```

---

## 30. Additional data-quality rules

For each business key, verify:

```
1. not more than one current row
2. valid_from < valid_to
3. no overlapping intervals
4. mandatory business key
5. unique surrogate key
```

For example, this is a problem:

```
2025-01-01 → 2026-08-01
2026-06-01 → 9999-12-31
```

For the period:

```
2026-06-01 → 2026-08-01
```

We have two valid versions.

## 35. Late-arriving facts

An interesting problem arises when we receive an old transaction today.

For example:

```
today: 2026-09-23

the transaction received:
TRANSACTION_DATE = 2025-08-10
```

The customer is now:

```
PREMIUM
```

But in 2025 it was:

```
RETAIL
```

We don't have to choose simply:

```
current_flag = 'Y'
```

We have to look at the time:

```sql
SELECT customer_sk
FROM dim_customer
WHERE customer_id = :customer_id
  AND :transaction_date >= valid_from
  AND :transaction_date <  valid_to;
```

This ensures that the fact row receives the correct historical surrogate key.

### How would you briefly explain Slowly Changing Dimensions to a colleague who knows SQL but not this area?

Slowly Changing Dimensions (SCD) define how a Data Warehouse preserves or overwrites changes in dimension attributes over time. The key concepts are SCD Types 0, 1, and 2, hybrid approaches, business keys, surrogate keys, `VALID_FROM`, `VALID_TO`, and `CURRENT_FLAG`.

### What are two common practical problems related to Slowly Changing Dimensions?

Two recurring problems are incorrect temporal logic—such as overlapping versions or multiple current rows—and incorrect change detection. At scale, lookup strategy and set-based processing also become important.

### How do you check that the result is correct and not just fast?

I compare the number of rows, amounts and keys with the source or with a reference result; I test NULLs, duplicates, limits and rerouting of the batch.I only then check time, resources and execution plan.

### What information did you collect before you modified an existing solution?

I collect the functional requirement, grain, business keys, surrogate-key strategy, tracked attributes, expected volume, validity rules, dependencies, batch behavior, known errors/logs, and acceptance criteria. I also define how failed loads can be rolled back or rerun safely.

### Give an example of a DWH or banking flow where this concept changes design.

In a banking DWH, SCD logic is closely connected to logging, auditing, reconciliation, lineage, and impact analysis because historical reports must resolve the dimension version that was valid when each business event occurred.

depends on the business requirement.
