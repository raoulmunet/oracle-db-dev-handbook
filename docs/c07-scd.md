# C07. Slowly Changing Dimensions

<div className="chapter-kicker">Chapter C07 · Complete course</div>

Slowly Changing Dimensions (SCD) are the techniques by which a Data Warehouse manages changes in time of the attributes of a dimension.

The central idea is simple:

> **What do we do when a descriptive attribute of an entity changes, but do we possibly want to keep old value?**

Examples:

- a customer changes its city;
- a customer passes from the RETAIL segment to PREMIUM;
- an employee changes the department;
- a product changes its category;
- one branch passes into another region.

For an Oracle Data Developer, the most important are **SCD Type 1 and SCD Type 2**, and Type 2 is one of the most common concepts of DWH in the technical discussion.

---

## 1. Why do we need SCD?

Suppose we have:

```
CUSTOMER_ID = 1001
NAME = Ionescu
CITY = Bucharest
```

The client is moving to Brașov.

In the source system, we often simply have:

```
CUSTOMER_ID = 1001
NAME = Ionescu
CITY = Brasov
```

But in a Data Warehouse, the question arises:

```
I want to know where the ACUM client lived?
```

or:

```
I want to know where the client lived
at the time of the 2025 transaction?
```

The two questions require different models.

This is where SCD comes in.

---

# 2. The Two Essential Types

## SCD

The old value is **overwritten**.

We don't keep history.

```
before

CUSTOMER_ID CITY
-----------   ----------
1001 Bucharest
```

After modification:

```
CUSTOMER_ID CITY
-----------   ----------
1001 Brașov
```

We can no longer find out from DWH that the client previously lived in Bucharest.

---

## SCD Type 2

We're not simply changing the line.

Instead:

1. close the old version;
2. We're inserting a new version.

Result:

```
CUSTOMER_SK CUSTOMER_ID CITY VALID_FROM VALID_TO CURRENT_FLAG
----------- ----------- ---------- ---------- ---------- ------------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
245 1001 Brașov 2026-06-01 9999-12-31 Y
```

We now have a full history.

---

# 3. Natural Key vs Surrogate Key

This concept is fundamental to SCD Type 2.

Suppose in the operational system the client has:

```
CUSTOMER_ID = 1001
```

This is:

```
Business Key
or
Natural Key
```

In DWH we insert an artificial key:

```
CUSTOMER_SK
```

for example:

```
101
245
387
```

The structure shall become:

```
CUSTOMER_SK surrogate key
CUSTOMER_ID business key
```

Why?

Because the same client may have several versions.

```
CUSTOMER_SKQ1QX CITY
----------- ----------- ----------
101 1001 Bucharest
245 1001 Brașov
```

Business key is the same:

```
CUSTOMER_ID = 1001
```

but each version has another:

```
CUSTOMER_SK
```

# 5. Example SCD Type 1

Initial:

```
CUSTOMER_ID CITY
----------- ----------
1001 Bucharest
```

In staging comes:

```
CUSTOMER_ID CITY
----------- ----------
1001 Brașov
```

We can update using:

```
UPDATE dim_customer
SET city = 'Brașov'
WHERE customer_id = 1001;
```

Or for ETL charges:

```
MERGE INTO dim_customer
USING staging_customer
ON (d.customer_id = s.customer_id)

WHENQ1QX THEN
UPDATE SET
d.customer_name = s.customer_name,
d.city = s.city,
d.segment = s.segment

WHEN NOT MATCHED THEN
INSERT
(
customer_id,
customer_name,
city,
segment
)
VALUES
(
s.customer_id,
s.customer_name,
s.city,
ssegment
);
```

This is a typical implementation for:

```
SCD
```

# 6. When do we use SCD Type 1?

When history isn't important.

Examples:

```
correction of a typo
```

for example:

```
Bucharest
```

becomes:

```
Bucharest
```

There's no point in keeping:

```
Version 1: Bucharest
Version 2: Bucharest
```

Other example:

```
customer_name:
IONSCU
```

corrected at:

```
IONESCU
```

Type 1 is right.

# 7. SCD Type 2

Suppose we have:

```
Customer 1001
City = Bucharest
```

Current row:

```
CUSTOMER_SK = 101
CUSTOMER_ID = 1001
CITY = Bucharest
VALID_FROM = 2025-01-01
VALID_TO = 9999-12-31
CURRENT_FLAG = Y
```

At:

```
2026-06-01
```

The client is moving to Brasov.

We don't:

```
UPDATE dim_customer
SET city = 'Brașov';
```

Because I'm losing track of history.

---

# 8. Step 1) Closing the Old Version

```
UPDATE dim_customer
SET valid_to = DATE '2026-06-01',
current_flag = 'N'
WHERE customer_id = 1001
AND current_flag = 'Y';
```

Now:

```
CUSTOMER_SK CUSTOMER_ID CITY VALID_FROM VALID_TO CURRENT
----------- ----------- ---------- ---------- ---------- -------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
```

---

# 9. Step 2 insertion of the new version

```
INSERTQ1QX dim_customer
(
customer_id,
customer_name,
city,
segment,
valid_from,
valid_to,
current_flag
)
VALUES
(
1001,
'Ionescu',
'Brașov',
'RETAIL',
DATE '2026-06-01',
DATE '9999-12-31',
'Y'
);
```

Result:

```
SK ID CITY VALID_FROM VALID_TO CURRENT
---  ----  ----------  -----------  -----------  -------
101 1001 Bucureşti 2025-01-01 2026-06-01 N
245 1001 Brașov 2026-06-01 9999-12-31 Y
```

# 10. Time intervals

A good pattern is to treat intervals like:

```
* VALID_FROM, VALID_TO)
```

I mean:

```
VALID_FROM = date
AND
date
```

No:

```
BETWEEN valid_from AND valid_to
```

if VALID\ _ TO is the exact beginning of the next version.

For example:

```
Bucharest:
2025-01-01

BRASHOV:
2026-06-01
```

Advantage:

```
We have no overlaps.
We have no ambiguity at the border.
```

# 14. Detection of changes

In SCD2 we need to know if the data has even changed.

Simple version:

```
WHERE NVL (d.city, '#')
OR NVL (d.segment, '#')
```

But if the size is:

```
40
50
100
```

columns, the comparison becomes uncomfortable.

Then we can use a hash.

---

# 15. Change Detection with STANDARD\ _ HASH

For example:

```
STANDARD_HASH (
NVL (customer_name, '#')
* '|' *
(city, '#')
* '|' *
(segment, '#')
'SHA256'
)
```

We can store:

```
HASH_VALUE
```

in size.

At ETL we calculate the hashish for staging.

If:

```
source_hash = dimension_hash
```

then:

```
NO CHANGE
```

If:

```
source_hash - dimension_hash
```

then:

```
CHANGE DETECTED
```

and trigger SCD2.

# 20.SCD Type 3

Type 3 keeps the history in a limited number of columns.

Example:

```
CUSTOMER_ID
CURRENT_CITY
PREVIOUS_CITY
```

Initial:

```
1001; Bucureşti; NULL;
```

The client moves:

```
1001 - Brașov - Bucharest
```

If he moves back to Cluj:

```
1001 - Cluj - Brașov
```

We lost Bucharest.

So we only have limited history.

---

# 21. SCD Type 4

Type 4 uses two tables.

A table for the current value:

```
DIM_CUSTOMER
```

and another for the historian:

```
DIM_CUSTOMER_HISTORY
```

For example:

```
DIM_CUSTOMER

1001 - Brașov
```

and:

```
DIM_CUSTOMER_HISTORY

1001; Bucureşti; 2025-01-01; 2026-06-01
```

# 25. SCD and MERGE in Oracle

MERGE is very useful for:

```
SCD
```

but you need to pay attention to Type 2.

SCD2 assumes, for an amended row:

```
UPDATE old row
+
INSERT new row
```

The real implementation is therefore frequent:

```
UPDATE old versions
INSERT new versions
```

in two set-based operations or through an intermediate staging.

It should not be automatically assumed that a single simple MERGE solves the entire SCD2 elegantly.

---

# 26. Patterson Oracle set-based for SCD2

Suppose:

```
STG_CUSTOMER
DIM_CUSTOMER
```

We identify the changes:

```
SELECT
s.customer_id,
s.customer_name,
s.city,
ssegment
FROM staging_customer
JOIN dim_customer d
ON d.customer_id = s.customer_id
AND d.current_flag = 'Y'
WHERE NVL (s.customer_name, '#')
OR NVL (s.city, '#')
OR NVL (s.segment, '#')
```

---

# 27. Closure of modified versions

```
UPDATE dim_customer d
SET
d.valid_to = SYSDATE,
d.current_flag = 'N'
WHERE d.current_flag = 'Y'
AND EXISTS
(
SELECT 1
FROM staging_customer
WHERE s.customer_id = d.customer_id
AND
(
NVL (s.customer_name, '#')
OR NVL (s.city, '#')
OR NVL (s.segment, '#')
)
);
```

---

# 28. Insert new versions

After detection of the changes, we insert the new versions.

In practice it is safer to have a list of changes in a staging / delta table before, because after UPDATE size no longer contains the same values with which we compared.

Conceptual:

```
STAGING
     ↓
CHANGE_SET
     ↓
UPDATE old DIM rows
     ↓
INSERT new DIM rows
```

This is a more robust pattern.

# 29. The Most Important SCD2 Rule

For a business key there must normally be:

```
not more than one CURRENT_FLAG = 'Y'
```

For:

```
CUSTOMER_ID = 1001
```

is wrong:

```
SKQ1QX CURRENT
101 1001 Y
245 1001 Y
```

Right:

```
101 1001 N
245 1001 Y
```

---

# 30. Other rules of Data Quality

For each business key must be checked:

```
1. not more than one current row
2. valid_from - valid_to
3. no overlapping intervals
4. mandatory business key
5. unique surrogate key
```

For example, this is a problem:

```
2025-01-01 → 2026-08-01
2026-06-01 → 9999-12-31
```

For the period:

```
2026-06-01 → 2026-08-01
```

We have two valid versions.

# 35. Late-arriving facts

An interesting problem arises when we receive an old transaction today.

For example:

```
today: 2026-09-23

the transaction received:
TRANSACTION_DATE = 2025-08-10
```

The client is now:

```
PREMIUM
```

But in 2025 it was:

```
RETAIL
```

We don't have to choose simply:

```
current_flag = 'Y'
```

We have to look at the time:

```
SELECT customer_sk
FROM dim_customer
WHERE customer_id =: customer_id
AND: transaction_date = valid_from
AND: transaction_date;
```

So the factman gets the correct historical version.

## Questions and answers

### How would you briefly explain the Slowly Changing Dimensions of SCD to a colleague who knows SQL, but not this area?

The Slowly Changing Dimensions (SCD) covers SCD Type 0, 1, 2 and hybrid approaches, business key vs surrogate key, valid _ from, valid _ to and current flag. In practice, I first determine what data enter and what result must be obtained, then I check implementation, execution plan and effects on flow.

### What are the two most common practical problems related to Slowly Changing Dimensions (SCD)?

Two recurring problems are the misinterpretation of data or granularity and degradation of performance at real volume. For the Slowly Changing Dimensions (SCD), I explicitly follow SCD Type 0, 1, 2 and hybrid approaches, business key vs surrogate key, valid _ from, valid _ to and current flag and compare the result with a control set.

### How do you check that the result is correct and not just fast?

I compare the number of rows, amounts and keys with the source or with a reference result; I test NULLs, duplicates, limits and rerouting of the batch.I only then check time, resources and execution plan.

### What information did you collect before you modified an existing solution?

I collect functional requirement, grain, scheme and keys, volume, data distribution, dependencies, plans and time, errors / lobes and acceptance criteria. I note how to return to the previous state.

### Give an example of a DWH or banking flow where this concept changes design.

In a bank flow, the Slowly Changing Dimensions SCD appears together with logging, auditing, reconciliation and impact analysis.
