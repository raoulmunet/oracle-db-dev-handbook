# C33. Data Modeling

<div className="chapter-kicker">Chapter C33 · Complete course</div>

**Data Modeling** means transforming business requirements into a coherent data structure: **entities, attributes, relationships, keys and integrity rules**.

For an Oracle Data Developer it is important to understand two main model families:

- **Relational / Normalised** modelling predominantly OLTP;
- **Dimensional modelling** is predominantly Data Warehouse / OLAP.

---

## 1. The 3 levels of modelling

We usually go through:

```
Business requirements
        ↓
Conceptual Model
        ↓
Logical Model
        ↓
Physical Model
        ↓
Oracle Database
```

### Conceptual model

Describe **what information** exists without technical details.

Example for banking:

```
CUSTOMER
ACCOUNT
TRANSACTION

CUSTOMER owns ACCOUNT
ACCOUNT has TRANSACTION
```

We're not interested yet:

- VARCHAR2;
- indexes;
- partitioning;
- Tablespace;
- technical columns.

It's the language closest to business.

---

## 2. Logical Model

The logical model introduces:

- entities;
- attributes;
- Major Keys,
- Foreign Keys,
- cardinalities;
- normalization.

Example:

```
CUSTOMER
--------
customer_id PK
first_name
last_name
birth_date

ACCOUNT
-------
account_id PK
customer_id FK
iban
balance

TRANSACTION
-----------
transaction_id PK
account_id FK
transaction_date
% 1
transaction_type
```

Relations:

```
CUSTOMER 1

ACCOUNT 1
```

I mean:

```
a CUSTOMER may have multiple ACCOUNT-uri
a ACCOUNT may have multiple TRANSACTION-uri
```

---

## 3. Physical Model

The physical model represents effective implementation in Oracle.

Example:

```
CREATE TABLE custodian (
customer_id NUMBER GENERATED BY DEFAULT AS IDENTITY,
first_name VARCHAR2 (100),
last_name VARCHAR2 (100) NOT NULL,
birth_date DATE,

CONSTRAINT pk_customer
PRIMARY KEY (customer_id)
);
```

```
CREATE TABLE account (
account_id NUMBER GENERATED BY DEFAULT AS IDENTITY,
customer_id NUMBER NOT NULL,
iban VARCHAR2 (34) NOT NULL,
balance NUMBER (18,2),

CONSTRAINT pk_account
PRIMARY KEY (account_id),

CONSTRAINT fk_account_customer
FOREIGN KEY (customer_id)
REFERENCES custodian (customer_id),

CONSTRAINT uq_account_iban
UNIQUE (iban)
);
```

Decisions such as:

```
NUMBER vs VARCHAR2
DATE vs TIMESTAMP
PK / FK
INDEX
PARTITIONING
COMPRESSION
TABLESPACE
IDENTITY / SEQUENCE
```

---

## 4. Entity, attribute and relationship

These are the fundamental elements of modelling.

## Entity

An object about which we store information:

```
CUSTOMER
ACCOUNT
PRODUCT
ORDER
TRANSACTION
EMPLOYEE
```

It usually becomes an TABLE.

---

## Attribute

An entity's property.

```
CUSTOMER
customer_id
first_name
last_name
birth_date
```

It usually becomes a column.

---

## Relationship

Describe the link between entities.

Example:

```
CUSTOMER owns ACCOUNT
```

Implementation:

```
ACCOUNT.customer_id
        ↓
CUSTOMER.customer_id
```

by FOREIGN KEY.

---

## 5. Cardinality

Cardinality describes **how many instances of one entity can be associated with another**.

The most important are:

```
1: 1
1: N
N: M
```

---

## 1: 1

Example:

```
EMPLOYEE Carol EMPLOYEE_BADGE
```

An employee has only one badge.

---

## 1: N

Very common.

```
CUSTOMER 1
```

The foreign key is on the N side:

```
account. customer_id
```

---

## 6. Relationship N: M

Example:

```
STUDENT N - + + + + + + + + + + + + +
```

A student can take a lot of classes.

A course can have many students.

In the relational model we do not directly implement the relationship N: M.

We use an **junction table / associate table**.

```
STUDENT
    |
    |
STUDENT_COURSE
    |
    |
COURSE
```

Example:

```
CREATE TABLE student_course (
student_id NUMBER,
course_id NUMBER,

CONSTRAINT pk_student_course
PRIMARY KEY (student_id, course_id),

CONSTRAINT fk_sc_student
FOREIGN KEY (student_id)
REFERENCES student (student_id),

CONSTRAINT fk_sc_course
FOREIGN KEY (course_id)
REFERENCES course (course_id)
);
```

Important pattern:

```
N: M
 ↓
bridge / associate table
```

---

## 7. Major key

The primary key uniquely identifies each row in a table.

Example:

```
PRIMARY KEY (customer_id)
```

Properties:

```
UNIQUE
NOT NULL
stable
minimal
```

Ideally, the key doesn't have to change.

---

## 8. Natural Key vs Surrogate Key

This is an important difference in Data Modeling.

## Natural Key

It comes from business.

Examples:

```
IBAN
CNP
product_code
employee_number
```

Example:

```
customer_code = 'CUST12345'
```

---

## Surrogate Key

It's artificially created by the system.

```
customer_id = 918273
```

In Oracle:

```
customer_id NUMBER GENERATED AS IDENTITY
```

or:

```
CREATE SEQUENCE seq_customer;
```

---

## Why are we using surrogate keys?

Because business keys can change.

For example:

```
customer_number
```

may be modified after a migration of the system.

In an DWH is very common:

```
CUSTOMER_SK
CUSTOMER_ID
```

where:

```
CUSTOMER_SK = guaranteed key DWH
CUSTOMER_ID = business / natural key
```

---

## 9. Candidate Key and Alternative Key

A table may have several columns that could uniquely identify a row.

Example:

```
CUSTOMER

customer_id
customer_code
email
```

Maybe:

```
customer_id = Primary Key

customer_code = Candidate / Alternative Key
```

Implementation:

```
CONSTRAINT uq_customer_code
UNIQUE (customer_code)
```

---

## 10. Normalization

Normalisation aims to reduce:

```
redundancy
abnormalities
inconsistencies
```

It's very important in OLTP.

Main forms:

```
1NF
2NF
3NF
BCNF
```

In practice, for reviews, the most important are **1NF, and 3NF**.

---

## 11. First Normal Form › 1NF

A column shall contain an atomic value.

Wrong:

```
CUSTOMER

customer_id
name
phones
```

where:

```
phones = '0722111111,0733222222'
```

Problem:

```
several values in a single column
```

Right:

```
CUSTOMER
CUSTOMER_PHONE
```

```
CUSTOMER
---------
customer_id

CUSTOMER_PHONE
--------------
customer_id
phone_number
```

---

## 12. Second Normal Form

You have to:

```
1NF
+
non-key attributes to depend on the entire key
```

It's particularly relevant when we have composite keys.

Wrong example:

```
ORDER_ITEM

order_id
product_id
product_name
quantity
```

PK:

```
(order_id, product_id)
```

But:

```
product_name
```

depends only on:

```
product_id
```

not the full key.

Right:

```
PRODUCT
-------
product_id
product_name

ORDER_ITEM
----------
order_id
product_id
quantity
```

---

## 13. Third Normal Form › 3NF

A non-key attribute shall not depend on another non-key attribute.

Wrong:

```
CUSTOMER

customer_id
city_id
city_name
country_name
```

We have:

```
customer_id → city_id
city_id → city_name
city_name → country_name
```

We have transitional dependencies.

Right:

```
CUSTOMER
CITY
COUNTRY
```

---

## 14. Why is OLTP usually normalized?

In an OLTP system we want:

```
Quick INSERT
UPDATE consistent
Safe DELETE
Reduced redundancy
High integrity
```

The model may look like this:

```
CUSTOMER
   |
ACCOUNT
   |
TRANSACTION
   |
TRANSACTION_TYPE
```

The data are distributed in several tables.

For the operational application this is very good.

For analytics, however, it can produce many joinings.

---

## 15. Deneromalization

Deneromalization intentionally introduces redundancy.

The aim is usually:

```
Simplification of queries
reduction of joins
increasing analytical performance
```

It is common:

```
Data Warehouse
Mart date
Reporting
OLAP
```

## 16. Dimensional modelling

In Data Warehouse we often use:

```
FACT TABLES

```

Example:

```
DIM_CUSTOMER
                 |
DIM_DATE - FACT_TRANSACTION - DIM_ACCOUNT
                 |
DIM_BRANCH
```

This is an **Star Schedule**.

## 17. Fact Table

Fact table represents a measurable business event.

Examples:

```
Its
payment
Bank transaction
order
balance account
website event
```

Example:

```
FACT_TRANSACTION

transaction_sk
date_sk
customer_sk
account_sk
branch_sk

% 1
fee
balance
```

The first columns:

```
date_sk
customer_sk
account_sk
branch_sk
```

There are keys to the dimensions.

Latest:

```
% 1
fee
balance
```

There are measures.

---

## 18. Size Table

Dimensions provide context.

Example:

```
DIM_CUSTOMER

customer_sk
customer_id
customer_name
customer_type
city
region
country
```

Allow analysis:

```
sales per customer
Transactions by region
Transactions by country
```

## 19. Grain

When designing a fact table, the first thing to be determined is:

> **What exactly is a row?**

This is the granularity of **grain**.

Example:

```
a row = individual banking transaction
```

or:

```
a row = balance of an account at the end of each day
```

These are completely different models.

---

## 20. Example of grain

For:

```
FACT_TRANSACTION
```

Grain:

```
one row per banking transaction
```

Then:

```
transaction_id
```

can identify the event.

But for:

```
FACT_DAILY_ACCOUNT_BALANCE
```

Grain may be:

```
one row per account per day
```

The logical key becomes:

```
account_sk + date_sk
```

---

## 21. Fact types tables

Three classic types.

## Transaction Fact

One round for each event.

```
FACT_TRANSACTION

TX001
TX002
TX003
```

Example:

```
payments
transfers
sales
```

---

## Periodic Snapshot

A regular snapshot.

Example:

```
Account balance at end of day
```

```
ACCOUNT
DATE
BALANCE
```

---

## Accumulating Snapshot

A row is updated during a process.

Example:

```
loan application
```

may contain:

```
application_date
approval_date
contract_date
disbursement_date
```

---

## 22. Types of Measures

In fact, we have measures.

Example:

```
% 1
quantity
fee
balance
```

I can be:

### Additives

They can be summed up in all sizes.

```
sales_amount
```

---

### Semi-additive

They can only be summed up in certain dimensions.

Example:

```
account_balance
```

You can collect account balances:

```
SUM (balance)
```

but it doesn't usually make sense:

```
SUM (balance) over days
```

---

### Non-additive

It doesn't add up directly.

Examples:

```
percenage
ratio
exchange_rate
```

## 23. Star Schema

Structure:

```
DIM_CUSTOMER
                   |
DIM_DATE - FACT_SALES - DIM_PRODUCT
                   |
DIM_STORE
```

Advantages:

```
Simple model
few joinings
easy for BI
clear queries
good performance
```

It's the most used dimensional model.

---

## 24. Snowflake Schema

Dimensions are normalized.

Example:

```
DIM_CUSTOMER
      |
DIM_CITY
      |
DIM_REGION
      |
DIM_COUNTRY
```

Instead of:

```
DIM_CUSTOMER

city
region
country
```

Advantage:

```
less redundancy
```

Disadvantage:

```
more joins
more complex model
```

In DWH, Star Schema is often preferred for analytical consumption.

---

## 25. Conformed Dimensions

A dimension used in multiple fact tables.

Example:

```
DIM_CUSTOMER
```

is used by:

```
FACT_TRANSACTION
FACT_LOAN
FACT_PAYMENT
```

So we can consistently analyze the same client in several processes.

This is a very important concept in the DWH enterprise architecture.

---

## 26. Roller-Playing Dimensions

The same size can have several roles.

Example:

```
DIM_DATE
```

used as:

```
order_date
shipping_date
payment_date
```

Logical:

```
DIM_DATE
                  ↑
          ┌───────┼────────┐
          │       │        │
order shipping payment
          │       │        │
¶ ¶ FACT_ORDER ¶ ¶
```

---

## 27. Degenerate Dimension

Sometimes a business identifier stays directly in the fact table.

Example:

```
invoice_number
transaction_reference
order_number
```

without separate table.

```
FACT_SALES

sales_sk
date_sk
customer_sk
product_sk
invoice_number
% 1
```

Invoice_number may be an **degenerate dimension**.

---

## 28. Junk Dimension

Small attributes, categorical, without their own natural dimensions can be grouped.

Example:

```
is_online
is_promotional
payment_type
priority_flag
```

may form:

```
DIM_TRANSACTION_FLAGS
```

This is called **junk size**.

---

## 29. Slowly Changing Dimensions

In dimensional modelling, we have to decide how we keep the changes in attributes.

Example:

```
customer.city

Bucharest
↓
Cluj
```

Main solutions:

```
SCD
SCD Type 2
SCD Type 3
```

The most important for DWH is often **SCD Type 2**.

Example:

```
customer_sk, customer_id, valid_from, valid_to, valid_to
------------+-------------+------------+------------+----------
1001, C100, Bucuresti, 2024-01-01, 2026-05-10
1847; C100; Cluj; 2026-05-11; 9999-12-31
```

So the history is preserved.

## 34. Example Oracle is a dimensional model

```
CREATE TABLE dim_customer (
customer_sk NUMBER PRIMARY KEY,
customer_id VARCHAR2 (30) NOT NULL,
customer_name VARCHAR2 (200),
city VARCHAR2 (100),
country VARCHAR2 (100),
valid_from DATE,
valid_to DATE,
is_current CHAR (1)
);
```

```
CREATE TABLE dim_date (
date_sk NUMBER PRIMARY KEY,
calendar_date DATE,
year_no NUMBER,
month_no NUMBER,
day_no NUMBER
);
```

```
CREATE TABLE fact_transaction (
transaction_sk NUMBER PRIMARY KEY,

date_sk NUMBER NOT NULL,
customer_sk NUMBER NOT NULL,

transaction_id VARCHAR2 (50),
amount NUMBER (18,2),
fee NUMBER (18,2),

CONSTRAINT fk_fact_date
FOREIGN KEY (date_sk)
REFERENCES dim_date (date_sk),

CONSTRAINT fk_fact_customer
FOREIGN KEY (customer_sk)
REFERENCES dim_customer (customer_sk)
);
```

Query:

```
SELECT
d.year_no,
d.month_no,
c. Country,
SUM (f.amount) total_amount
FROM fact_transaction f
JOIN dim_date d
ON d.date_sk = f.date_sk
JOIN dim_customer c
ON c.customer_sk = f.customer_sk
GROUP BY
d.year_no,
d.month_no,
c.country;
```

The model allows very natural analytical questions such as:

> What is the total value of transactions per month and country?

## 35. Indexation and modelling

Logical modelling and physical modelling are not the same thing.

Logical model:

```
CUSTOMER 1: N ACCOUNT
```

The physical model may include additional:

```
CREATE INDEX ix_account_customer
ON account (customer_id);
```

In Oracle it is important to remember:

> A FOREIGN KEY does not automatically create an index on the FK column.

In OLTP, indexes on foreign keys may be important for performance and locking depending on the operations performed.

---

## 36. Partitioning and modelling DWH

A large fact backgammon can be physically designed with partitioning.

Example:

```
CREATE TABLE fact_transaction (
transaction_id NUMBER,
transaction_date DATE,
amount NUMBER
)
PARTITION BY RANGE (transaction_date)
INTERVAL (NUMTOYMINTERVAL (1, 'MONTH'))
(
PARTITION p_initial
VALUES LESS THAN (DATE '2026-01-01')
);
```

The logical model says:

```
FACT_TRANSACTION
```

The physical model decides:

```
monthly partitions
indexes
compression
tablespaces
```

## 37. Common Mistakes by Data Modeling

### 1. Undefined Grain

The FACT_SALES is built without being clear what a row represents.

Consequences:

```
duplicate date
SUM wrong
ETL difficult
```

---

### 2. Mixing several grains

Wrong:

```
FACT_ACCOUNT

transaction rows
+
monthly balance rows
```

There are two different processes.

Better:

```
FACT_TRANSACTION
FACT_MONTHLY_BALANCE
```

---

### 3. Using business key as the only DWH key

It can create problems with:

```
SCD
changes in source
multiple source systems
```

---

### 4. Too much normalization in BI

Query:

```
FACT
JOIN DIM_CITY
JOIN DIM_REGION
JOIN DIM_COUNTRY
JOIN DIM_CUSTOMER_TYPE
...
```

can become unnecessarily complex.

---

### 5. Dimensions without History

If the businessman asks:

> In which region was the client when the transaction was made?

a simple SCD1 overwrite is not enough.

## Questions and answers

### What is the difference between conceptual, logical and physical model?

```
Conceptual
→ entities and business relationships

Logical
→ attributes, PK, FK, cardinalities, normalization

Physical
→ Oracle implementation:
datatype, index, partitioning, storage etc.
```

---

### What is the difference between OLTP and DWH modeling?

```
OLTP
→ normalized relational model

DWH
→ Dimensional model, often denormalized
```

---

### What's the grain?

> Grain defines exactly what a row is in a fact table.

It must be set before the measures and dimensions.

---

### Natural key vs surrogate key?

```
Natural key
→ business identity

Surrogate key
→ Artificial identity created by DWH
```

---

### Why are we using surrogate keys in DWH?

For:

```
SCD
historical
multiple source systems
insulation from business keys changes
```

---

### Star vs Snowflake?

```
Star
→ denormalised dimensions
→ Simple
→ Few joins

Snowflake
→ Normalised dimensions
→ more tables and joins
```

---

### What is a conformed dimension?

A reused dimension consistently in multiple fact tables.

Example:

```
DIM_CUSTOMER
```

used both for:

```
FACT_TRANSACTION
```

as well as for:

```
FACT_LOAN
```

---

### What kind of fact tables do you know?

```
Transaction Fact
Periodic Snapshot
Accumulating Snapshot
```

---

### What's a degenerate dimension?

A business-size attribute kept directly in fact table without separate table.

Example:

```
invoice_number
transaction_reference
```

### How would you briefly explain Data Modeling to a colleague who knows SQL, but not this area?

The Modeling data covers conceptual, logical and physical models, entities, attributes, relationships and cardinality, normalization for OLTP. In practice, I first determine what data enter and what result must be obtained, then I check implementation, execution plan and effects on flow.

### What are the two most common practical problems related to Data Modeling?

Two recurring problems are the misinterpretation of data or granularity and degradation of performance at real volume. For Data Modeling, I explicitly follow conceptual, logical and physical models, entities, attributes, relationships and cardinality, normalization for OLTP and compare the result with a control set.

### How do you check that the result is correct and not just fast?

I compare the number of rows, amounts and keys with the source or with a reference result; I test NULLs, duplicates, limits and rerouting of the batch.I only then check time, resources and execution plan.

### What information did you collect before you modified an existing solution?

I collect functional requirement, grain, schema and keys, volume, data distribution, dependencies, plans and time, errors / logs and acceptance criteria. I note how to return to the previous state.

### Give an example of a DWH or banking flow where this concept changes design.

In a bank flow, Data Modeling appears together with logging, auditing, reconciliation and impact analysis.
